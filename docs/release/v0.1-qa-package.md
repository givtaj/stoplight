## Public Alpha Contract — 2026-11-06

The first release target is **`v0.1.0-alpha.1`: a public GitHub repository plus a prebuilt extension ZIP**, selected by the maintainer on 2026-11-06. The repository is [givtaj/stoplight](https://github.com/givtaj/stoplight). This is a developer alpha: download, extract, enable Developer mode, and Load unpacked. It requires no Rust, Node.js, or build tools to install the ZIP. This is not a Chrome Web Store installation or automatic-update channel; [Chrome's distribution guidance](https://developer.chrome.com/docs/extensions/how-to/distribute) distinguishes unpacked development use from store distribution.

The supported workflow is one explicitly armed HTTP(S) tab, an origin allowlist, request-stage Fetch/XHR interception, textual header/body editing, Continue Unchanged, Continue Edited, Play All, and detach/re-arm. Multipart and binary bodies remain inspect-only. Publish the exact tested Chrome version and OS; Chrome 118 is currently the manifest/API minimum, not evidence that every Chrome 118+ version and OS was tested. One declared Chrome/OS combination is sufficient for this alpha; other combinations must be labeled unverified.

**Decision rule:** all gates A1–A6 must pass on the frozen candidate before publishing an alpha asset. A7 must then pass through the public download path before announcing the alpha as verified. An unknown, failed, or untested required behavior blocks the relevant gate. There is no score, coverage percentage, or majority vote that overrides a failed gate.

### Required Browser Matrix

Use controlled synthetic HTTP and HTTPS fixtures, including a second tab and a second origin. Assert delivery using the receiving server's bytes/headers, not only the extension's status text. Cover both Fetch and XHR across the core pause/continue cases. Record held requests before release and check for unexpected extra deliveries afterward.

| ID | Scenario | Pass condition |
| --- | --- | --- |
| B1 | Install and native Chrome panel | Toolbar action opens the actual native side panel; controls are usable and the correct website target is shown. Loading the panel HTML as a tab is insufficient. |
| B2 | Target and allowlist boundaries | Only the shown, explicitly armed tab and allowed origins pause. A changed target is rejected until reviewed. Other tabs, non-allowlisted origins, Chrome pages and the extension's own page are not armed accidentally. A matching request has not reached the fixture server while held. |
| B3 | Unchanged and edited requests | Continue Unchanged preserves original body bytes and application header semantics, even after changing the draft. Continue Edited sends exactly the intended headers/body once. Cover JSON, text with Unicode, urlencoded form, XML, nonempty-to-empty edits and a bodyless request. An unsupported edit must be visibly rejected before forwarding, with unchanged recovery available. |
| B4 | Queue and Play All | At least three requests are held, displayed in arrival order and released exactly once in that order. For alpha, Play All continues the original requests unchanged; unsent editor drafts are not applied. The UI explains this, and a test with an edited draft proves original bytes arrive. Each request settles and the queue drains. No claim that forwarding proves remote durable storage. |
| B5 | Static traffic | Image, stylesheet and script requests complete without entering or stalling the paused API queue. |
| B6 | Inspect-only bodies | Multipart with a file, octet-stream and another binary MIME such as `image/png` are noneditable and continue without byte corruption. Unavailable or truncated captured bodies are labeled accordingly, never treated as a safely editable empty body. Header-edit controls agree with the stated inspect-only contract. |
| B7 | Invalid edits and command failures | Invalid header names/newlines and a failed continuation produce visible errors, no unintended send, and an available unchanged/detach recovery path. Repeated button clicks do not duplicate delivery. |
| B8 | Session lifecycle | Explicit detach, opening DevTools, closing the target tab and worker restart produce truthful visible state. Held requests settle or visibly fail and the page/session can recover; no silently stranded traffic. Re-arm succeeds where the tab remains available. Observe network/page results, not just a cleared UI queue. |
| B9 | Privacy and permissions | Installed permissions match documented reasons; Stoplight initiates no undeclared third-party transmission. Inspect browser storage before/after detach and browser-session end, including request headers/bodies; document actual retention and clearing controls. |
| B10 | Removal and manual update | Detach then disable/remove releases control and leaves normal requests working. Follow documented manual replacement/reload instructions without silently rearming a tab. First alpha rollback is detach/disable/remove; do not invent an earlier release. |

Manual evidence may replace missing/flaky edge-case automation for this alpha **only for the exact named scenario on the same ZIP**, with steps, actual result and server/browser evidence. The static-asset and multipart skips may remain recorded as skips until automated; they are never passes. Binary coverage still needs its own evidence. Preserve a separate automation backlog.

### Historical Source-review Concerns — Resolved in Selected Candidate

Reviewed source baseline: `90abfd9cd7892573b219002016714b3063a9bd64`. These historical findings were addressed in compiled source `48c3d6f`; [source review](source-review-2026-11-06.md) and the [selected verification receipt](alpha.1-verification.md) record closure. The findings below describe the earlier baseline:

- [`build_continue_payload`](../../crates/core/src/request.rs) omits `post_data_base64` for an empty edit; [`continueRequest`](../../extension/src/background/controller.ts) then omits `postData`. The [CDP Fetch contract](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/#method-continueRequest) applies body overrides only when supplied. B3 must prove that clearing a body sends zero bytes or is explicitly rejected, rather than silently sending the original.
- [`decode_body`](../../crates/core/src/body.rs) treats missing/empty captured data as editable and only explicitly classifies `application/octet-stream` as binary. Other binary MIME types can remain editable. B6 must close this gap, including absent capture data.
- [`continueUnchanged`](../../extension/src/background/controller.ts) uses the same header/body reconstruction as edited continuation. B3/B6 must prove preservation. The [`side-panel controls`](../../extension/src/sidepanel/main.ts) also allow header editing for inspect-only bodies; reconcile this with [`PLAN.md`](../../PLAN.md)'s unchanged-only contract.
- The existing [`detach browser test`](../../extension/tests/e2e/stoplight.spec.ts) checks UI clearing without checking that held network traffic settles. Worker restart hydration likewise needs transport-level proof under B8.

## Historical Manual Smoke Checklist — 2026-10-09

Retained for provenance. Use the packaged-candidate B1–B10 matrix above for the alpha; this older build-from-source checklist is not its acceptance procedure.

Run these steps on a clean Chrome profile with Chrome 118+.

1. Build the unpacked extension from the repository root.
2. Open `chrome://extensions`, enable Developer mode, and load `extension/dist/`.
3. Open a simple test site that issues XHR/fetch requests from the active tab.
4. Open Stoplight from the toolbar action and arm the current tab.
5. Confirm the side panel shows the intended website arm target, allowlist, and idle session state.
6. Trigger a matching request and confirm it pauses in the queue.
7. Select the paused request and verify the headers/body editors are populated.
8. Edit a JSON or text request and continue edited, then verify the server receives the edited payload.
9. Queue two matching requests and confirm Play All releases them in arrival order.
10. Continue one request unchanged and verify the original payload is sent.
11. Detach the session or open DevTools and confirm the UI flips to detached and requires re-arm.
12. Verify multipart and binary requests are visible but not editable.
13. Verify static assets are auto-continued and do not pollute the paused queue.
